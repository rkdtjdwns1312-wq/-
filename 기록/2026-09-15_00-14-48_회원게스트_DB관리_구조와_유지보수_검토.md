# 회원·게스트 DB 관리 구조와 유지보수 검토

- 요청: 088
- 기록 시각: 2026-09-15 00:14:48 한국 시간
- 범위: 현 구조 확인과 유지보수 방안 설명. 구조 변경·운영 데이터 수정 요청은 아님.
- 수행: Codex 본체 직접 소스 확인·검토. 단순 자문으로 하위 에이전트 위임 없음.

## 확인 결과

- 작업 전 origin main에 pull --ff-only 실행, Already up to date. 조회 시작 작업 트리 깨끗함.
- 회원은 D1 `ranking_members`, 게스트는 `guests` 테이블에 저장된다.
- `dist/server/boards.js`의 GET /api/people 및 GET /api/rankings는 DB를 조회한다. 사람 추가·숨김·회원 이관 및 대진 정산도 DB를 변경한다. 현재 데이터 수정이 매번 코드 명단을 덮어쓰는 방식은 아니다.
- `roster.js`와 `rankings.js`의 initialRankingRows는 초기 명단 역할로 남아 있다. ensureRankingMembers·ensureGuests는 여러 조회/관리 요청에서 INSERT OR IGNORE를 반복 실행한다. 기존 ID의 행은 덮어쓰지 않는다. 숨긴 사람도 행을 유지하므로 단순 조회로 다시 보이게 된다고 단정할 수 없다.
- DB 바인딩이 없을 때 /api/people만 코드 명단을 반환하는 예외 경로가 있다. 운영 환경에서 오래된 명단이 대신 표시되는 혼란을 방지하려면 명시적 장애 응답으로 정리할 후보이다.
- 기존 사람 추가·숨김·이관 기능과 경기 정산 이력은 이미 있다. 기존 이름/점수의 범용 직접 수정 화면과 수동 변경 전후·사유 이력은 별도 보완 후보로 구분한다.

## 권장 방향 — 미구현 제안

1. 현재 Cloudflare D1을 그대로 사용한다. 다른 DB 서비스 도입이나 전면 재작성은 필요하지 않다.
2. 회원·게스트 운영 정보는 DB만 기준으로 삼는다. 코드에는 점수·시드 산정과 권한 등 동작 규칙을 둔다.
3. 정적 초기 명단을 조회 시마다 처리하지 않도록 일회성·버전 관리된 초기 등록/마이그레이션으로 분리한다. 기존 DB에 최신 점수를 옛 초기값으로 재삽입·덮어쓰면 안 된다.
4. 실제 변경 요청 시 먼저 백업하고 기존 ID·점수·순위 변동·보호 상태·대진·정산 이력 및 회원 이관 연결을 보존한다. 이후 운영진 수정 UI와 변경 이력 보완을 검토한다.
5. 회원/게스트 테이블 통합은 필수가 아니다. 현재 규모에서는 두 테이블을 유지하며 중복 처리만 줄이는 점진 개선이 위험·개발비 대비 유리하다.

효과는 불필요한 초기화 요청 감소, 코드와 운영 데이터 책임 분리, 배포 없이 명단 관리 가능성 확대이다. 큰 속도 향상이나 구체적인 비용 절감 수치는 측정하지 않았으므로 보장하지 않는다.

참고: [Cloudflare D1 migrations 공식 문서](https://developers.cloudflare.com/d1/reference/migrations/)에서 SQL 파일별 버전과 적용 이력을 관리하는 방식을 확인했다.

## 변경·검증·인계

- 변경 파일은 메인.md와 이 설명 기록뿐이다.
- 소스 추적 기반 자문이며 이번 요청으로 기능 테스트·운영 데이터 쓰기·commit/push·자동 배포를 실행하지 않았다. 설명만 요청한 범위를 지키기 위해 문서는 로컬 저장했다.
- 실제 구조 개선은 사용자가 진행을 요청하면 위 보존 조건을 기준으로 설계·테스트 후 수행한다. 이를 이미 승인되거나 구현된 작업으로 취급하지 않는다.

## 핵심 명령

현재 시드현황의 실제 DB 저장 구조를 확인하고, 기존 D1을 유지하면서 코드의 초기 명단 의존성을 정리하는 유지보수 방안을 설명한다. 설명 요청만으로 운영 DB나 기능 코드를 변경하지 않는다.
